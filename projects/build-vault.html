Build Vault

Send it a link to a build video and it returns a working plan: what the project actually is, what the video oversold, the cheapest route to the same result, and a numbered sequence to follow. It runs entirely in the browser with no server and no database to operate.

01 The problem

A saved video is not a plan

Short-form video is full of people building genuinely useful things, and it is a terrible format for learning how to build them. The interesting part goes by in two seconds of screen recording, the voiceover is written to sell rather than to explain, and the comments never contain the one detail that would let you start.

Saving those videos produced a folder of things I could not act on. What I wanted was the opposite of a bookmark: a short, honest read on what the project really involves and a first step concrete enough to begin on a weeknight.

02 How it works

Four stages

StageWhat happens
CaptureA video link is pasted in, or handed over from the phone's share sheet. A typed description works too, and costs nothing to process.
ReadThe spoken transcript and a separate visual read of the screen are pulled from the video, because the two carry different information.
PlanA language model fills a fixed schema: what it is, what is required, an ordered set of steps, and a cheaper alternate route.
KeepThe record is written to the browser's own database and synced across devices, with a status you can move from idea to building to done.
03 Design decisions

Key design decisions

Read the screen, not just the audio

The obvious build is transcript-only, and it is the wrong one here. In a build video the narration is promotion; the actual evidence is on screen in the terminal, the file tree and the typed commands. So the visual read runs on every single save rather than as a fallback when the transcript is thin.

That decision costs real money, roughly nine credits for a ninety-second video against a free allowance of a hundred a month, which works out to about eleven saves. I took that ceiling deliberately and added the typed-description path, which uses no credits at all, to take pressure off it. Knowing the budget before committing to the design is the whole point.

Separate what was shown from what was inferred

A plan that quietly presents a guess as an observation is worse than no plan. Every step carries a flag for whether it was actually visible in the video, and every item in the tooling list carries a confidence level. The schema also has a field for what the video oversold, and a separate one for whether the thing is buildable at all, which catches videos that are really advertisements for a paid product and files them somewhere else instead of throwing them away.

Sync with no infrastructure

Capture happens on a phone and the actual work happens on a laptop, so the two libraries had to agree without introducing a server. Records sync through a private repository over the ordinary web API, last write wins per record. Deletions write a tombstone rather than simply disappearing, because without one the other device helpfully restores everything you just deleted. A failed sync never blocks the app; the local copy stays authoritative.

Spending less on the easy case

Videos that cover several projects at once are common, so a cheap first pass just counts them and asks which one to plan, and only then runs the expensive reasoning pass on the one you picked. Single-project videos skip the question entirely. The expensive read of the video happens once regardless, so a video covering five projects costs the same as one covering a single project.

04 Why it belongs here

Relevance to engineering work

This is a requirements problem wearing a different hat. An unstructured source gets read, the claims in it get separated from the evidence for them, the result gets forced into a fixed schema, and what could not be verified is labelled as such. That is the same discipline as writing a test report where measured values and assumptions do not get to share a column.

The cost decision is the one I would defend hardest. A fixed monthly allowance is a constraint like any other, and the design was set against it on purpose: pay for the read that carries the real information, add a free path to relieve the ceiling, and never pay twice for the same input.

The honest part

Eleven video saves a month is a real ceiling, and it is the thing most likely to frustrate someone else using it. The free typed-description path softens that, but it does not remove it, and a paid tier would be the correct fix rather than a cleverer workaround.

The output is also only as good as what a video actually shows. When a creator skips the hard part, the plan honestly reports low confidence instead of inventing the missing step, which is the right behaviour but not a satisfying one. If I rebuilt it, I would spend the effort on turning those low-confidence gaps into specific questions worth researching rather than leaving them as a flag.
