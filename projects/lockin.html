01 The problem

Logging a workout is not programming one

Most training apps are spreadsheets with nicer fonts. They record what you did and leave the actual question, what you should do next week, entirely to you. The apps that do decide for you tend to hide the reasoning, so when the number they hand you is wrong there is no way to tell whether it is wrong because the model is bad or because you had a bad night's sleep.

I wanted the decision itself written down as rules I could inspect, argue with, and test.

02 How it works

The progression engine

The core is a set of deterministic rules, not a model call. Double progression drives load and reps within a set range. Weekly volume climbs from a starting landmark toward a ceiling across a block and then deloads. A readiness input regulates the whole thing, so a week of poor sleep pulls the prescription down instead of marching the plan off a cliff.

ComponentWhat it computes
ProgressionNext session's load and reps, from the previous session's performance against a target rep range.
Block structureVolume ramped from a starting landmark to a ceiling across a training block, then a deload.
Auto-regulationReadiness inputs scale the prescription up or down rather than overriding it.
AnalyticsEstimated one-rep max, tonnage, weight trend, per-muscle heatmap, weekly score and streaks.
NutritionMacro targets from a standard metabolic-rate equation, with food lookup by search or barcode.
03 Design decisions

Key design decisions

Test the maths, because nobody notices when it drifts

A wrong stress calculation announces itself when the part breaks. A wrong training calculation just quietly gives you a slightly stupid workout for six weeks. So the arithmetic is covered by a regression suite of 369 checks that runs in the browser: progression cases worked by hand, calendar-week handling swept across four years of dates to catch year-boundary bugs, score components verified to sum correctly, and the one-rep-max and metabolic-rate formulas checked against textbook values rather than against themselves.

Keep the model on a short leash

The language model does the part it is genuinely good at, turning a messy description into structure, and is kept away from the part it is bad at, which is arithmetic. Every call goes through a strict schema, and every call is proxied through a small server-side worker so the API keys never reach the browser. The worker fails closed by design: it rejects the wrong method, rejects an unapproved origin, and rejects a request without a valid signed-in token.

Constraints first: two users, zero dollars

This was never going to be a product, so I designed against the real constraints instead of imaginary ones. Two accounts, a free hosting tier, and free API tiers set the budget at nothing per month, and that budget is what chose the architecture: static hosting, a generous free-tier worker, and a hosted database with rules doing the authorisation rather than a server I would have to maintain.

Verifying the locks, not assuming them

Security rules that have never been tested are decoration. After deploying, I probed the live database directly with unauthenticated requests against both users' records and their subcollections and confirmed every read and every write came back denied, and checked the worker returned the right refusal for a hostile origin, a missing token, and a wrong request method. Writing the rule and confirming the rule are two different jobs.

04 Why it belongs here

Relevance to engineering work

Progressive overload is a control problem. There is a plant that responds to input with delay and noise, a target trajectory, and a feedback signal that is partly unreliable. The interesting engineering is in the same places it always is: choosing what to trust, deciding how hard to correct when the feedback is bad, and building in a scheduled backoff so the system does not accumulate damage.

The habit I actually carried over from the capstone is verifying rather than assuming. Hand-checking a progression case against the rules is the same instinct as hand-checking an FEA result against a closed-form calculation before believing the colours.

The honest part

It is built for two specific people and it shows. There is no onboarding to speak of, the training conventions it encodes are opinionated choices rather than settled science, and nothing about the data model anticipates a third user with different preferences. That was the right call for the scope, but it is a rewrite, not a toggle, if it ever needs to serve strangers.
