03 The interesting parts

Three problems worth talking about

Security rules are the actual product

Client-side checks are decoration; the only thing standing between one user's data and another's is the Firestore rules file. I wrote and published rules enforcing that a user can read and write only documents under their own UID, and that league membership requires a valid invite code rather than merely knowing a group ID. Then I verified them end-to-end against the live backend — signing in as a second account and confirming the reads actually fail — rather than trusting that the rules said what I thought they said.

Migrations, because users already have data

Once somebody is relying on the app, every schema change is a compatibility problem. The CSV import path handles older column layouts and fills in fields that did not exist when the row was written, so a release never orphans existing data. This is the same discipline as revision-controlling a drawing package: the new version has to account for what was already built to the old one.

Service worker caching that does not serve stale code

A PWA that caches aggressively will happily serve last week's JavaScript forever. The service worker uses a versioned cache name that is bumped on release, so phones pick up new builds instead of pinning to whatever they installed first.

Transferable to engineering work

Access control, versioned data, and graceful handling of the old revision are not web-specific ideas. They are the same concerns as controlled drawings, revision letters and interchangeability — which is most of why building this made me better at the documentation side of the capstone.
