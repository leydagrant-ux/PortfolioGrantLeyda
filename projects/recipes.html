Recipe Book

An application that turns a cooking video into a structured, searchable recipe. It pulls the spoken transcript, has a language model extract the ingredients and numbered steps, and stores the result in a single portable database, images included, so the library outlives the original post.

01 The problem

Saved videos are not a recipe collection

Cooking videos are a genuinely useful source of recipes and a genuinely terrible way to store them. The instructions are spoken rather than written, quantities go by too quickly to note, and a saved post is not searchable. Worse, a bookmarked video is only as permanent as the account that posted it.

I wanted the underlying recipe as text I own: searchable by ingredient, readable in the kitchen, and still there in two years.

02 How it works

Four stages

StageWhat happens
CaptureA share-sheet shortcut posts the video URL to the API, no app switching.
TranscribeThe service returns the spoken transcript plus the caption text.
ExtractA language model turns that prose into a structured recipe: title, quantified ingredients, numbered steps, notes on servings and substitutions.
StoreThe recipe and the cover image are written to SQLite and indexed for search.
03 Design decisions

Key design decisions

Store the image bytes, not the link

The obvious implementation saves the thumbnail URL. That quietly fails: those URLs are signed and expire, and creators delete posts. A library built on links degrades to blank tiles over a matter of months. The application downloads the image at save time and writes the bytes into the database, so a saved recipe does not depend on anything outside the file.

Make the whole library one file

Everything (recipes, metadata and images) lives in a single SQLite file. Backing up the library is copying one file, and moving it between machines needs no export step. For a personal-scale application, that portability is worth far more than the performance a heavier database would buy.

Never pay twice for the same video

Transcription and extraction both cost money per call, so saving a video that is already in the library returns the stored copy rather than reprocessing it. Requests are validated before any paid call is made, and a video with no readable instructions is rejected outright instead of being half-saved.

Error handling

Every failure mode returns a specific, correct HTTP status rather than a generic error: a malformed link, a missing credential, a video with no usable text, an upstream service outage, and a transcription timeout are all distinguishable by the response. That distinction is what makes the shortcut on the phone able to tell the user something useful when a save does not work.

04 Why it belongs here

Relevance to engineering work

Underneath the subject matter, this is a data-pipeline problem: take an unstructured input, extract the fields that matter, validate them, and store the result in a form that stays usable over time. The same shape appears in test-data reduction, inspection records and any workflow that turns measurements into a report.

The durability decision is the one I would defend hardest in either context. Choosing to store the bytes rather than the reference is the same instinct as keeping a controlled copy of a drawing rather than a link to wherever it happened to live.
